## Verdict

Wire's core value proposition — compile-time dependency-injection codegen that resolves a DAG of provider functions into a generated `Initialize...` function — has no anchor point in `symaira-corekit`. Corekit is explicitly a flat, "Standalone-First" library (see `README.md:9-16`): its 11 packages are independent, do not depend on each other, and have no injector-style composition root to generate. That mismatch fails gate 1 (Transferable) for nearly every wire-specific pattern (provider sets, `wire.Bind`, `wire.Struct`, mock-injection idioms), and the repo is also archived, which caps confidence further. One idea does survive the gates and is unrelated to DI itself: wire's CI script that runs `apidiff` on every PR to catch accidental breaking Go API changes before merge. That is a concrete, currently-missing safety net for a library that promises "Strict SemVer" to several downstream consumers.

- Wire's matrix CI across OSes (`ubuntu`, `macos`, `windows`) → `.github/workflows/ci.yml:18` already runs `ubuntu-latest` + `macos-latest`; Windows is covered separately via `fsutil/safewrite_windows.go`'s existing platform split rather than full-matrix CI, which is proportionate to corekit's size.

## Findings

- [ ] **[UX/DX] Add an automated Go API-compatibility check to CI**
  - **Status quo:** `symaira-corekit` promises "Strict SemVer" (`README.md:44`) and is pinned by version in every consumer's `go.mod` (`ECOSYSTEM.md:157`), but nothing in `.github/workflows/ci.yml` verifies that a PR doesn't silently break the public API. The only breaking-change signal in the whole toolchain is the release skill's reliance on a human-written conventional-commit marker (`!` or `BREAKING CHANGE`, per `~/.claude/skills/07-gh-release/SKILL.md:133`) — if a contributor removes an exported field or changes a signature without flagging it, the release tooling computes the wrong SemVer bump and nothing catches it before merge. Upstream `google/wire` solves exactly this with `internal/check_api_change.sh`, wired into `tests.yml` on every push/PR: it installs `golang.org/x/exp/cmd/apidiff`, diffs the branch's exported API against upstream `main` for every non-internal package, and fails the build on any incompatible change unless the commit message contains `BREAKING_CHANGE_OK`.
  - **Proposed solution:** Pattern adoption, not code copy (script is trivial to rewrite for this repo's `main` branch name and doesn't need porting verbatim). Add a `govulncheck`-style job to `.github/workflows/ci.yml` (there's already a working precedent for installing a Go analysis tool in CI at `ci.yml:52-58`) that runs `apidiff` against `origin/main` for each package under `go list ./... | grep -v _test`, fails on incompatible changes, and is bypassable via a commit-message escape hatch consistent with the existing `BREAKING CHANGE` marker convention already used by `07-gh-release`.
  - **Effort/Impact:** Low effort (one CI job, ~40 lines, no new runtime dependency) / medium impact — directly backs the "Strict SemVer" promise with enforcement instead of manual discipline, and reduces the chance of an unflagged breaking change reaching a consumer repo pinned to corekit.

## Considered and rejected

- **Provider sets / `wire.NewSet`, `wire.Build`, `wire.Bind`, `wire.Struct`, `wire.FieldsOf`** — gate 1 (Transferable): these exist to resolve a dependency graph across many provider functions into a generated composition root. Corekit's own contract forbids that graph from existing between its packages (`README.md:9-16`); the wiring these would solve happens in each consumer's separate `main.go` repo, which is out of scope for this TARGET.
- **Wire's "Provider Sets in Libraries" compatibility rules (`docs/best-practices.md`)** — same underlying idea as the API-compat finding above (define what's a safe vs. breaking change to a versioned Go library surface), but the wire-specific rules are about provider-set conflicts, not general Go API surface; the `apidiff`-based finding already captures the transferable part in a more general, tool-enforced form.
- **Wire's mocking idioms (Approach A/B, injected mocks)** — gate 1 (Transferable): both approaches exist to substitute mocks into a generated injector graph; corekit has no injector graph to substitute into.
- **CONTRIBUTING.md's CLA + biweekly triage + milestone process** — gate 9/scale fit: built for a Google-run OSS project with external contributors; `symaira-corekit` is a solo repo with no external contribution flow to triage.
- **`cmd/wire` CLI (subcommand-based code-generation tool)** — gate 2 (New) / not applicable: corekit is a library, not a CLI; the ecosystem's CLIs live in separate consumer repos, out of scope for this TARGET.
- **Wire's `internal/wire/testdata`-driven golden-file test suite for the analysis engine** — gate 2 (New): corekit already uses the same testdata pattern where it has generative/parsing logic to golden-test (`sqlitekit/testdata/migrations/`); wire's version is scaled to a much larger code-analysis engine that corekit doesn't have.

## Open questions

- None — the mismatch between wire's DI-graph mechanism and corekit's deliberately graph-free architecture was clear from the TARGET's own README contract, and the one surviving finding (`apidiff` in CI) is self-explanatory from its upstream script.

The single best first step: add an `apidiff`-based breaking-API-change CI job to `.github/workflows/ci.yml`, modeled on wire's `internal/check_api_change.sh`, so the repo's "Strict SemVer" promise is enforced mechanically rather than left to commit-message discipline.
